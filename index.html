Lesson 01 · Tool design

The first version is
deceptively simple.

client → MCP server → ticketing API | +-- tool: search_tickets That is a working MCP server. Then the real requests arrive: create one, comment on one, close one a safer default than "return everything" what "no results" means, so it stops retrying who is allowed to call the write tools and how anyone finds the server at all
Lesson 01 · Tool design

At a handful of tools,
naming is the interface at dozens.

The early question

"Can the model call this API?"

The later question

"Can a developer understand and operate this tool safely?"

search_tickets(query, status, requester_email, limit) is easier to use — and safer — than: request(path, method, query, body) The second one is less code for me and every decision for the model.
Lesson 01 · Tool overload

More tools didn't mean
more capability.

— BEFORE — query_records query_with_filter query_with_fields query_object_structure query_work_orders query_assets query_locations ... Every name correct. The model still picked wrong.
— AFTER — list_schemas what can I query? get_schema what fields exist? run_query ask the question Three tools instead of seven. Selection stopped being a coin flip.
Technically precise.
Operationally confusing.
Lesson 02 · The tool is not the API call

The hardest tool wasn't
the complicated one.

SHIPPED

create_ticket

Two parameters. Returned 201 Created every single time.

BROKE

Wrong owner

The requester was my API service account, so the platform mailed every reply to the bot — not the customer.

FIXED

Requester attribution

Create on behalf of the real customer, so the whole downstream email thread routes correctly.

Try it: call create_ticket in mcp-ticket-demo without requester_email, then look at who owns the ticket.

A tool isn't done when the API call succeeds.
It's done when the next thing that happens is right.
Lesson 03 · Developer experience

A tool is a UI for an agent.
An extension is a UI for the developer.

Import

Read the mcp.json that's already in the workspace instead of asking anyone to retype it.

Diagnose

Credential, health, tools/list, then one real call — each step pass or fail, in order.

Test

Call any tool with real arguments and read the raw response, without leaving the editor.

It turns "something is broken" into "this step failed, here's why, here's what to try next."

Lesson 04 · Local isn't remote

Zero tools discovered.
No error. No warning.

# What I registered command: node args: ["/Users/markus/mcp-ticket-demo/…"] → 0 tools discovered The runner is a cloud container. It looked for /Users/markus/… → not there. A missing file reads as an empty tool list.
# What actually works command: node args: ["src/index.js"] cwd: relative to the package I shipped → 9 tools discovered ✓ Same code. Same command. Different execution context.

Secrets move

Off the laptop and into the platform.

Diagnostics stop being optional

/health, /test, /admin earn their keep.

The URL isn't stable

A new project means a new hostname. Never paste it into mcp.json.

Lesson 04 · The messy parts

The failures that
taught me the most.

What I sawWhat was actually wrongWhat I changed
0 tools discoveredI gave a cloud runner a path from my laptopShip the package, run from a relative path
A strange vendor error, never a 404Wrong API host — the bad hostname answered with something else entirelyPin the confirmed host and assert it at startup
Auth looked fine, every call failedA required tenant header was missingCheck required headers before the first call, not after
mcp.json worked yesterdayRedeploying gave the service a new hostnameRead the endpoint after deploy; never paste a URL by hand
The model picked the wrong toolSeven near-identical query_* namesOne query tool plus schema discovery
Client hung, or a JSON parse errorconsole.log("connected") wrote into the stdio streamLog diagnostics to stderr — console.error

Most of these failed silently. The parse error named nothing useful either. That's the pattern I'd warn my past self about.

Lesson 05 · Permission

Who is allowed to call it?
The protocol doesn't say.

# What I shipped first 403 Forbidden The model retried. Then retried again. Then told the user the system was "unavailable."
# What it says now create_ticket needs "write". This key has [read]. Issue one with that scope on /admin → API keys. → it asks for a key instead of looping.
A locked tool still shows up in tools/list.
The refusal is the only place left to explain yourself.

Three modes in the demo: off on your laptop, write so reads stay open and writes need a key, all for anything with a public URL. Discovery stays open in every mode — a client that can't ask "what do you need from me?" can only guess.

Lesson 06 · The next server

Copy the boring parts.
Leave the tools alone.

Server two made me want one library for everything. The only things that were actually the same: the folder, the README, how it starts, how it fails. Searching a ticket is not deploying a container.

Copy this

  • Same folder and README shape
  • Same env and startup checks
  • Same error shape and logs
  • Same version notes
  • One test that it starts

Don't copy this

  • Ticket search is not cloud deploy
  • A read is not a write
  • Your laptop is not a public URL
  • Work login is not a local key
Lesson 07 · Documentation

The README is
part of the API.

  1. What does this server do, and who is it for?
  2. Which tools are available?
  3. How do I install and configure it?
  4. What does a real call look like?
  5. What permissions and risks should I understand?
  6. What happens when it fails?
  7. Where do I report a problem?

Screenshots are nice. A copyable path is better.

Lesson 08 · Discoverability

Publishing isn't the same as
being findable.

I published on all four channels people use: marketplaces, npm, GitHub, IDE extensions.

What works

Searching the product name. Someone who already uses Zendesk types "Zendesk MCP" and lands on my server, first page.

What doesn't

Searching for what you need. Nobody finds a server by asking "what can triage a ticket?" — and an agent can't search at all.

Three things would fix it. I can't build any of them — none live in my code:

01

Search by capability

Let an agent ask "who can triage a ticket?" instead of needing the exact name.

needs: the protocol

02

Verified publisher

Give "is this really from Zendesk?" an answer you can check.

needs: the registries

03

Install at runtime

Add a server without a human hand-editing mcp.json first.

needs: the clients

The readiness test

Does it work out of the box?
For a developer, and for a model.

The developer reads the README

  • Running in ten minutes — timed, clean machine
  • At least one real call with real output, not just a parameter table
  • Edge cases written down: empty result, rate limit, expired token, partial failure
  • Honest about limits, cost, and what it can't do
  • Where to report a problem

The model reads the schema

  • Names that say what they do without the source
  • Descriptions that say when to use it, not just what it does
  • Every parameter with a type, a default, and an example value
  • What "no results" means — an empty array is not "try again". Say stop.
  • Errors phrased as next actions, because it will act on them
The model never opens your README.
The description field is the entire manual it gets.
The opportunity

MCP servers can become
more than integrations.

They can be the layer your team stops worrying about — because it behaves the same way every time, explains itself when it doesn't, and can be found without asking me.

Good tools.
Clear docs.
Honest metadata.
A place to find them.

Honest metadata — everything a person or an agent reads before installing: what it touches, which permissions it wants, what it was tested against, whether anyone still maintains it. A 1.0.0 on an abandoned server is the same lie as a 200 OK on a broken outcome.

Appendix · Publish

Ship the package.
Then ship the name.

The registry does not host your code. npm does. Publish npm first, or the name publish fails.

  1. Bump the version in two files — package.json and server.json, same number.
  2. Publish the package — npm publish --access public from server/, not the repo root.
  3. Wait about a minute. npm is not instant.
  4. Publish the name — mcp-publisher publish. Then open both pages.

If it has an extension: package the .vsix and upload it to Open VSX. The registry name must start with io.github.youruser/.
